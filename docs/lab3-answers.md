# Lab 3: відповіді на питання

## Міграція

**1. Що в Stage 0 тарифікується погодинно і чим це замінено.**
- ALB: зник. Lambda має власний HTTPS-ендпоінт (function URL).
- Публічні IPv4 (2 на ALB, 1 на задачі Fargate): зникли разом з ALB. Мережеві інтерфейси Lambda у VPC приватні.
- Задача Fargate: замінена на Lambda, яка тарифікується за запити й GB-секунди, а не за години.
- RDS db.t3.micro: замінено на Aurora Serverless v2 з 0 ACU, яка в паузі платить лише за сховище.
- (Сховище gp2 тарифікується за GB-місяць, а не за годину; в Aurora воно стало меншим.)

**2. За що ми платимо, коли платимо за ALB і IPv4.**
За досяжність: постійно увімкнену точку входу, яка приймає TCP/TLS, перевіряє здоров'я цілей і балансує навантаження, а також за дефіцитну публічну IPv4-адресу (з 2024 року AWS бере $0.005/год за кожну). Жоден із цих ресурсів не виконує нашого коду.

**3. Хто платить за 15 с пробудження Aurora.**
Користувач, який прийшов першим після тиші: він чекає. Компанія за це нічого не платить, навпаки, економить. Для демо, внутрішнього інструменту чи staging це прийнятно. Для публічного продукту, де перший запит — це перше враження або платіж, і для API з таймаутами клієнтів це баг.

**4. Чому повернувся CORS і як отримати один origin знову.**
У Stage 0 сторінка і `/api/*` йшли з одного хоста CloudFront. Тепер сторінка приходить з `app.…`, а API з `*.lambda-url.on.aws`: інша схема+хост+порт, тобто інший origin. Щоб повернутися до одного origin, треба додати function URL як другий origin у CloudFront з поведінкою `/api/*` (з OAC для Lambda, щоб function URL не був відкритим), а фронтенд має викликати відносний `/api/...`.

**5. Цикл «фронтенд потребує URL API, API потребує URL фронтенду».**
Makefile спершу деплоїть бекенд з CORS `*` (фронтенду ще немає), потім фронтенд з уже відомим URL API, а наступний деплой бекенду звужує CORS до outputs фронтенд-стеку. Той самий цикл є з Cognito: app client потребує callback URL сайту, а сайт потребує client ID і домен Cognito на етапі збірки. Тут його розриває те, що URL сайту відомий заздалегідь (власний домен), тому стек auth деплоїться першим, а фронтенд збирається з його outputs.

**6. Чому немає NAT gateway і що зламається.**
Lambda у VPC отримує лише приватні IP; без NAT вона бачить тільки ресурси VPC. NAT коштує ~$33/міс, більше за весь стек. Того дня, коли функція має звернутися до зовнішнього API (LLM-провайдер, Stripe, навіть Cognito JWKS або Secrets Manager без VPC endpoint), запити зависатимуть до таймауту. Варіанти: NAT gateway, VPC endpoints для сервісів AWS, або винести виклик у другу функцію поза VPC.

**7. Ціна переїзду в us-east-1.**
Для користувачів в Україні кожен виклик API отримує ~+90 мс (≈120 мс до Вірджинії проти ≈30 мс до Франкфурта); статика не страждає, бо її віддає edge CloudFront. Для компанії з клієнтами з ЄС персональні дані зберігаються в США: потрібні правова підстава для передачі (DPF/SCC), оновлення політики приватності та DPA; деякі клієнти (держсектор, медицина) цього взагалі не приймуть.

## Вартість

**8. Моє розгортання Lab 2.**
Мій стек — це Stage 0 у eu-central-1: ALB + 1 задача Fargate (0.25 vCPU) + RDS db.t3.micro. Він коштує ≈ $52/міс за цінами us-east-1 (у Франкфурті більше) незалежно від трафіку. Реальне використання — це рядок «ніхто не користується» (кілька перевірок викладачем), тобто Stage 2 обійшовся б приблизно в $0.30–1.50 на місяць.

**9. Uptime-монітор пінгує `/health` щохвилини.**
Мій `/health` не звертається до бази. Якби звертався, Aurora ніколи не заснула б (пауза лише після 5 хв без з'єднань): 730 год × 0.5–1 ACU × $0.12 ≈ $44–88/міс замість ~$0. Виправлення: `/health` перевіряє лише живість процесу, а перевірку бази винести в окремий `/health/db`, який викликають рідко (наприклад, раз на годину) або лише під час деплою.

**10. Коли повертатися до контейнерів і RDS.**
Коли Aurora не спить більше ~35% місяця (≈257 год при 0.5 ACU), RDS-інстанс дешевший; коли трафік сягає ~42M запитів/міс (~16 rps цілодобово), Fargate+ALB дешевші за Lambda. У Cost Explorer з фільтром за тегом `PROJECT_NAME` варто стежити за usage type `Aurora:ServerlessV2Usage` (ACU-години за місяць) та за Lambda `Request` і `Lambda-GB-Second`, порівнюючи їх з фіксованою ціною інстансу та задачі.

**11. Чому Free Tier — погана основа для рішення.**
Він закінчується (12 місяців або $200 кредитів за 6 місяців), а архітектура лишається. Він приховує саме ту статтю, яка визначає профіль витрат (погодинні ALB/RDS), і не масштабується: друге середовище або другий акаунт вже платять повну ціну. Рішення треба порівнювати за прейскурантними цінами.

## Автентифікація

**12. ID token і access token.**
ID token — це твердження для клієнта про те, *хто* користувач (email, name, `aud` = client ID); його читає фронтенд. Access token — це дозвіл викликати ресурс (scopes, `client_id`, `token_use: access`); саме він іде до API в `Authorization: Bearer`.

**13. Публічний клієнт і PKCE.**
Браузер не може зберегти секрет: будь-хто побачить його в JS. Без секрету вкрадений authorization code (з історії, логів, через перехоплення redirect) можна обміняти на токени. PKCE прив'язує code до одноразового `code_verifier`, який знає лише вкладка, що розпочала вхід, тобто для кожного входу виникає власний секрет. Від цього ж захищав би client secret: він не дав би стороннім обміняти перехоплений code.

**14. Cognito Essentials на 50 000 MAU.**
Перші 10 000 MAU безкоштовні, решта 40 000 × $0.015 ≈ $600/міс. Власну автентифікацію варто розглядати, коли рахунок за MAU стає порівнянним з вартістю інженера, який її підтримує (сотні тисяч MAU), або коли потрібні можливості, яких Cognito не має. Зазвичай спершу переходять на іншого керованого провайдера або self-hosted Keycloak, а не пишуть свою.

**15. Два користувачі з однаковим email.**
Ламаються таблиці, що посилаються на користувача через `sub`: зустрічі/власність, налаштування, ролі. Людина «губить» свої дані, коли входить іншим способом. Зв'язування: `AdminLinkProviderForUser` прив'язує Google-ідентичність до наявного нативного користувача (найкраще після того, як користувач увійшов обома способами й підтвердив зв'язок). Автоматично за email небезпечно: email від провайдера може бути непідтвердженим або контрольованим нападником (наприклад, створеним у провайдері, що не перевіряє email), і тоді нападник отримує чужий акаунт.

**16. Чому Google-секрет може бути в Cognito, а в app client секрету немає.**
Cognito — це сервер: секрет зберігається у сервісі AWS і ніколи не потрапляє до браузера, тож Cognito є конфіденційним клієнтом для Google. App client працює в браузері користувача, де будь-який «секрет» публічний, тому замість нього використовується PKCE.

**17. Що користувач бачить на consent screen Google.**
Назву застосунку, логотип, домен (`spry-koval.auth.us-east-1.amazoncognito.com`/домени з Branding), запитані дані (email, профіль) та посилання на політику приватності. Це важливо проти фішингу: користувач має бачити, *кому* він віддає дані. Застосунок із чужою назвою або підозрілим доменом — сигнал зупинитися; для цього Google і перевіряє брендинг застосунків, що запитують чутливі scopes.
