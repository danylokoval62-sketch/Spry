# Spry

Застосунок для зустрічей: список зустрічей і форма додавання нової.

- **Frontend**: React + Vite, Tailwind, shadcn/ui (S3 + CloudFront)
- **Backend**: FastAPI, SQLAlchemy, Alembic (ECS Fargate за Application Load Balancer)
- **База даних**: PostgreSQL 16 (Amazon RDS)

| Фронтенд | https://app.spry-koval.me |
| Бекенд | https://api.spry-koval.me (`/health`, `/api/meetings`) |

## Запуск локально

docker compose up --build

## Чому монорепозиторій

Backend, frontend, конфігурація бази та CI живуть в одному репозиторії з двох причин.

1. **Атомарні зміни.** Один коміт змінює і API, і клієнт, який його викликає, тому контракт між ними не може розійтися.
2. **Репозиторій як контекст.** Коли вся система в одному дереві, агент (або людина) за один прохід бачить ендпоінт, модель, міграцію та компонент, який їх відображає. Якби система була розбита на три репозиторії, він бачив би лише третину і вгадував решту, а вгаданий контракт стає помилкою на інтеграції. Це компроміс між незалежністю та контекстом: для команди з чотирьох людей і продукту, якого ще не існує, контекст важить більше.

## Деплой

Деплой описаний у `Makefile`, і CI виконує ті самі цілі, що й розробник локально:

- `make lint`: ruff для backend, ESLint і Prettier для frontend
- `make deploy-backend`: збірка образу, push в ECR з тегом = SHA коміту, оновлення ECS-сервісу
- `make deploy-frontend`: збірка, синхронізація з S3, інвалідація кешу CloudFront

Образи тегуються SHA коміту, а не `latest`, тож завжди відомо, який коміт зараз працює, а відкат означає розгортання попереднього тега.

Workflow `.github/workflows/ci.yml`: на кожен push запускається lint, а на гілці `main` після нього виконується деплой.

## Авторизація CI в AWS: OIDC

GitHub Actions не зберігає довготривалих ключів AWS. Замість цього:

1. GitHub видає підписаний токен із описом цього запуску (репозиторій і гілка).
2. AWS довіряє OIDC-провайдеру GitHub і дозволяє цьому токену отримати роль (`sts:AssumeRoleWithWebIdentity`).
3. `aws-actions/configure-aws-credentials@v4` обмінює токен на тимчасові облікові дані, які діють лише до кінця job.

Trust policy ролі обмежена **одним репозиторієм і однією гілкою `main`**. Умова перевіряє значення `sub` токена, а не шаблон на кшталт `repo:*`, інакше роль могла б отримати будь-який репозиторій GitHub.

Зараз GitHub формує `sub` у вигляді з числовими ID власника і репозиторію, а не просто з їхніх імен:

repo:danylokoval62-sketch@<owner-id>/Spry@<repo-id>:ref:refs/heads/main

Тому trust policy порівнює саме цей рядок. Значення `sub` було з'ясовано, виведши claims токена в запуску workflow.
